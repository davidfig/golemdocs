# Desktop app

The desktop app is a [Tauri](https://tauri.app) shell around the website, plus a *vault*: one folder on the computer that holds a copy of the account's documents as real files, kept in sync both ways (like an Obsidian vault). It is also how AI works with Golem Docs: the app has none of its own, and an external agent (Claude Code, Codex, Cursor...) reads and edits the vault's files, which sync back to the account like any other change. The same shell is meant to carry the iOS and Android apps later (Tauri 2 targets them).

## How it works

```
 desktop/src-tauri (Rust)                       client/src/desktop (page)
 ------------------------                       -------------------------
 window --> loads https://golemdocs.com  <----  the web app, unchanged: same code, sign-in, account
            (dev: http://localhost:5173)
 vault.rs: choose / scan / read / write ----->  bridge.ts   typed calls on window.__TAURI__
           / remove inside ONE folder           vaultPlan.ts  what a sync does (pure, tested)
```

- **The window shows the website**, not a bundled copy. Cookies, OAuth redirects and `/api` stay same-origin, so sign-in and the server need no changes. `desktop/frontend/index.html` is only the launcher: it opens the site, or says it cannot be reached. (A bundled, offline-capable client needs token auth on the API and is a later step.)
- **The page reaches the native side only through the vault commands**, and only the origins listed in `desktop/src-tauri/capabilities/default.json` may call them. `build.rs` registers each command so it has its own permission.
- **The vault commands never take a folder from the page.** The person picks it in a native dialog (`vault_choose`); Rust keeps it (remembered in the app's config folder) and every command takes a path *inside* it. `vault::resolve` refuses `..`, absolute paths, backslashes, dot-names and anything that goes through a symbolic link. Dot-names are not documents (`scan` skips them); `.golemdocs/` holds the sync state and only `vault_read` and `vault_write` may touch it.
- **Writes are atomic**: a hidden temporary file in the same folder, then a rename.

## The sync rule: the local file wins

**First launch.** `connectVault` (`main.ts`) opens the Vault Folder dialog once, on a device where no folder is remembered (signed in or not). `word.vaultAsked` in localStorage records that it was shown (per device, not synced), so closing the dialog without choosing is final; File › Vault Folder stays available.

**Without an account.** The folder does not need one. `syncVault` talks to a `VaultCloud` and cannot tell what is behind it: signed in it is `accountCloud()` (`vaultHost.ts`), signed out it is `guestCloud()` (`vaultGuest.ts`), the documents with no owner saved in this browser (`storage/local.ts`) and the folders kept here. Replacing one keeps a version in the browser's history and a deleted file goes to the browser's trash, so the same rule holds. The vault's `state.json` records whose folder it is (`GUEST_ACCOUNT` or an account id): a signed-out folder is taken over by the account that signs in (no memory, so files are matched to documents by path and the file wins), but a folder linked to an account is never given to another account or used signed out (`wrongAccount`, shown as "sign in to that account"), because documents copied out of it would be uploaded again by the sign-in's adoption of guest documents. `VaultService` waits for the page's uploads (`hooks.settled`) before the first sync as an account, so adopted documents are already there to match; it calls `hooks.changed` after a sync that changed anything, so the page's library list refreshes. The dialog words signed-out text with the `*Local` strings.

**The open document.** `SyncReport.touched` lists the documents a sync replaced, renamed or deleted on the other side (ids as that side knows them). `vaultChanged` (`main.ts`) refreshes the library and, if the open document is one of them and has no unsaved edits and is not in a shared room, stores the account's new copy (`openFromCloud`) and puts what is stored into the open document in place (`refreshFromStore`, the worker's `refresh`): `diffDocuments` (`ops/src/diff.ts`) turns the file's new content into operations against the open document, which `Editor.external` applies as someone else's edit would be (only the changed paragraphs are laid out again, the caret moves with its text, Undo doesn't take the change back). The page sends the point at the top of the view; the worker turns it into a text position and, in each layout update until the pages are laid out, sends where that text is now (`LayoutUpdate.keep`), so the view stays on it. The text that came in is highlighted green and fades out over two seconds (`SelectionUpdate.changes`, drawn by `SelectionLayer.changesFor`). The diff is checked by applying it to a copy; when it can't reproduce the file (styles, sections, comments or headers changed, a picture was added, a renamed file, a text file in the large-text editor, a PDF, picture or drawing), the document is opened again from storage (`openLocal`), which keeps its caret and scroll. The file wins either way; edits not yet saved (or made while the file is read) are left alone and the next sync decides.

Whatever is done to the folder is what the account becomes. That is safe because the account keeps history: replacing a document keeps its old bytes as a version first (`keepCloudVersion`), and deleting one moves it to the account's trash for 30 days ([Version history](../history.md)).

`planVault` (`client/src/desktop/vaultPlan.ts`) is a pure function of the files on disk, the manifest from the last sync and the account's catalogue. A sync is two steps: `needsHash` names the few files that must be hashed (those whose size or time moved, and possible renames), then `planVault` returns the actions.

| Situation | Action |
| --- | --- |
| New document in the account | `download` |
| Changed in the account, file untouched | `download` |
| File edited here (bytes differ, not just the time) | `upload`, even if the account changed too (then the account's bytes are kept as a version first) |
| New file | `create` |
| File deleted here | `deleteCloud` (account trash) |
| File moved or renamed here (same bytes, one candidate) | `renameCloud`; the document and its history stay one |
| Moved or renamed in the account, file untouched | `moveLocal` |
| Deleted in the account, file untouched | `deleteLocal` |
| Deleted in the account, file edited here | the edit is kept as a new document |
| Vault filled before it was linked | `upload` over the account copy (version kept) |
| Many files missing at once (10 or more, and half of those linked) | held back (`blocked`, `mass-delete`) until the person confirms: it is far more likely a drive that is not mounted |
| Many documents gone from the other side at once (the same numbers) | held back (`mass-delete-here`) before their files are deleted: more likely cleared storage or a memory that is not this side's |

Files are followed by their cloud id in the manifest, never by path. `cloudPaths` turns the account's folders and names into vault paths: it replaces characters a disk refuses, and keeps two same-named documents apart with " (2)" by creation order so a path is stable from one sync to the next.

## The sync driver

`syncVault` (`client/src/desktop/vaultSync.ts`) runs one sync against a `VaultHost` (disk, account, converter, hashing), so it is tested entirely in memory (`client/test/vaultSync.test.ts`). It lists the account, scans the folder, hashes only what `needsHash` names, runs `planVault`, executes the actions, and saves the manifest in this computer's memory of the vault.

**The manifest is per computer, not in the folder.** A vault folder may itself be shared with other computers by iCloud Drive, Dropbox, OneDrive or the like, and each computer links the files to its own documents (signed out, they are its own browser's). A manifest kept in the folder would reach the others and name documents they never had, and their sync would read that as "deleted on the other side" and delete every file. So the manifest is a `VaultMemory` (`vaultMemory.ts`: its own IndexedDB database, `golemdocs-vault`, one record per folder path), and the folder's `.golemdocs/state.json` only says whose it is (`account`, no entries), so a folder linked to an account is refused signed out or by another account on every computer that shares it (`wrongAccount`). A memory that can't be read stops the sync before it changes anything. With no memory, the sync takes in once the manifest an older version kept in the folder; signed out, entries none of whose documents this browser has are dropped (`adoptable`), whether they came from another computer or outlived cleared storage, so the files are taken in as new documents instead of being deleted. Two signed-in computers of the same account can share a folder too: ids are the account's, and a change that reaches the second computer through the folder and through the account is uploaded once more, at worst an extra version. One action failing is reported and the rest carry on; whatever failed still differs from the manifest, so the next sync retries it.

- **`vaultHost.ts`** is the real host: the native bridge, `cloud.ts` (a save without `base`, because the file wins; `saveCloudVersion` first when the account changed too; the trash for deletes) and folder creation by name.
- **`vaultService.ts`** keeps it running while the app is open: a stat-only scan every 4 seconds (no file-watcher dependency), the account every minute and when the window is shown or the connection returns. A sync's own writes are not counted as changes. Syncs never overlap. It is started from `connect()` in `main.ts`, so it follows sign-in and sign-out.
- **Permission.** `vault_check` (`vault::check_access`) reads the folder and writes then removes a hidden probe file. `VaultService.syncNow` calls it first on every sync: the first read of a protected folder (Documents, Desktop, iCloud Drive) is what makes macOS ask the person, and a refusal becomes the `access` state with the reason in `message`. An `access` folder is not retried every few seconds: Try Again (`retry`), or coming back to the window, asks again, and on a Mac `vault_open_privacy` opens System Settings › Files & Folders. A scan that fails in `look` now runs a sync, so the reason is reported instead of swallowed. The problem is shown once as a notice (`main.ts`), in the Vault Folder dialog and in the save indicator's panel.
- **How a file crosses.** `vault_read_base64` and `vault_write_base64` carry a file as base64 text (`{ path, data }`; `vault::base64_encode`/`base64_decode`, hand-written, and `toBase64`/`fromBase64` in `bridge.ts`). A string is one JSON value whichever way the web view sends it: when it won't use the custom-protocol request (the page is on another origin, or one fetch failed, and Tauri switches to `postMessage` for the rest of the session), raw bytes become a JSON array of numbers, several times the size and far too slow for a PDF of tens of megabytes (the account takes up to 50 MB a file). An older shell has only `vault_read` and `vault_write` (the file as the raw body, the path in a header; `vault::body_bytes` also takes the array form): the bridge falls back to them the first time a base64 command is missing (`isMissingCommand`) and stays there.
- **Show in Finder.** `vault_reveal` opens the vault's root in the system file manager (`open`, `explorer`, `xdg-open`); the page names no path. The save indicator's panel (`ui/syncButton.ts`, through `ChromeHost.vaultFolder`) shows the folder with this link, or a link to the Vault Folder dialog while none is chosen.
- **Progress.** `syncVault` reports each step (`SyncProgress`: access, uploads, account, folder, compare, then `done`/`total` and the path of each action) and the counts it found (`accountDocs`, `folderFiles`); the service keeps the step in `VaultStatus.progress` with the time it began, and the dialog words it and warns when one step has gone on for 20 seconds. Nothing can wait for ever: the page's uploads are waited for at most 20 seconds, and `ConvertWorker` fails a conversion after 60 seconds.
- **`ui/vaultDialog.ts`** (File › Vault Folder, desktop only): choose or change the folder, stop, sync now, status, and the confirmation for a held-back mass delete.

## What a file is on disk

`vaultCodec.ts`. **The file on disk is the result; the account keeps how you got there.** The account stores each document as a `.wdoc` (see [Formats](formats.md)): the model, the original PDF, a picture's layers, a drawing's objects, a PDF's annotations, fields and edits. The vault holds the file any other program opens, in the format its name asks for (`vaultFormat`, `vaultFormats.ts`), so an agent or another app can work on the documents in the folder:

| On disk | Going out (`toVaultFile`) | Coming back (`fromVaultFile`) |
|---|---|---|
| Word, ODT, RTF, HTML, EPUB, MHTML, Markdown, text and source files, CSV/TSV, the markup formats, DocBook/JATS/FB2/OPML, EML, notebooks | `exportDocument` with the container's extensions (Markdown front matter and the like come back exactly); Word is kept byte for byte both ways | `importDocument`, wrapped as a `.wdoc` with that format as its lens |
| PDF | the original with its annotations, fields and edits written in (`annotatedPdf`, `formats/pdfFile.ts`, the same function Download uses); a PDF whose reflowed text was edited is laid out from the text, as Download does | the new original, with no reflowed text and nothing done to it (the annotations, fields and edits of the old one are gone with it) |
| PNG, JPEG, WebP | the picture with its layers drawn in (the picture handler's `write`) | the picture, with no layers |
| SVG, SVGZ | the drawing's SVG; for a drawing edited together, made from its objects (`withDrawingText`, `formats/drawingText.ts`, shared with the layout worker) | the drawing |
| `.doc`, GIF, BMP, HEIC (read, never written) | as uploaded while the account holds the uploaded file; once the app has saved it, what the app edits it as (Word, PNG, JPEG) under the same name, which other programs recognise by its content | as is, as an upload: the app reads it when it is opened |

A file changed on disk replaces the document, which the account keeps a version of: the same "file wins" rule as for text. A document the account holds as the file it was uploaded as goes out unchanged when its name says that format. The vault leaves alone only names no format reads (a `.zip`, a `.wdoc`, no extension). A file renamed to another extension is saved again in the new format.

**Fonts.** Text formats need none. A PDF's edits set text in the app's fonts, and a PDF laid out from text, or a picture or drawing of a page of text, measures and draws it, so for those (`DRAWN`) the codec hands the writer the app's `FontSet`, loaded in the convert worker the first time one asks, the same way the layout worker loads it (`formats/appFonts.ts`: the manifest first, a face's metrics, atlas or font file only when used). A picture's or a PDF's own pages read nothing from it. The alternative, sending such documents to the layout worker, would tie the sync to whatever the editor has open and to its thread; the convert worker is already where every conversion runs.

Conversion runs on another thread. `convertWorker.ts` (started through `convertWorkerEntry.ts`) runs `vaultCodec.ts`; `convertClient.ts` (`ConvertWorker`, the `VaultCodec` the sync uses) sends it bytes and gets bytes back. The worker starts with the first conversion and ends after 30 seconds with nothing to do, so a vault that is only watched holds no converters in memory; one that dies fails what it was doing and the next sync retries it. The page asks only `vaultFormats.ts` (names, no converters) which files the vault keeps. Like the layout worker, the build keeps the worker's code in a chunk of its own (`vaultCore`, see `worker` in `client/vite.config.ts`), because WebKit, which Tauri uses on macOS, runs a worker's entry script again when a lazy chunk imports it. The converters are only fetched in the desktop app; the sync code in the page is about 14 kB (5 kB gzipped), too small for a chunk of its own.

## Updates

The shell updates itself through `tauri-plugin-updater`: `UpdateService` (`client/src/desktop/updateService.ts`) asks the shell shortly after start and every 6 hours whether a newer signed version exists (`update_check`, `desktop/src-tauri/src/update.rs`), the Software Update dialog (`ui/updateDialog.ts`, also Help › Check for Updates) offers it, and `update_install` replaces the app and restarts it. "Later" holds an offer back for a day per version (`word.updateSnooze`, per device). How releases are signed and published is in [Releasing the desktop app](desktop-release.md#updating-the-shell).

## The Mac menu bar

On a Mac the desktop app shows the menus in the system's menu bar and hides the ones above the document (`MenuBar.setNative`); other systems keep the in-page menus. There is still one list of menus (`Chrome.menus()` in `ui/chrome.ts`) and one set of commands, so nothing is defined twice:

```
 Chrome.refresh() --> NativeMenuSync.schedule()  (150 ms, then only if the menus differ)
                          snapshotMenus(): labels without mnemonics, accelerators, enabled/checked, ids
                          --> invoke set_native_menu --> menu.rs builds the Menu --> app.set_menu
 click or shortcut --> menu.rs emits "native-menu" (item id) --> NativeMenuSync.run(id) --> the command
```

- **Snapshot** (`client/src/desktop/nativeMenu.ts`): the same filtering as the page (`visibleItems`, `hasAvailable`); submenus built on open (Open Recent, samples) are read when the snapshot is made; a heading becomes a row that cannot be chosen. Ids belong to one snapshot; the actions are kept beside it.
- **Native side** (`desktop/src-tauri/src/menu.rs`): adds the app menu (About, Services, Hide, Quit) and a Window menu around the page's menus. An accelerator the system cannot parse drops only the shortcut, not the item.
- **Shortcuts are bound by the menu**: the system takes a key that matches a menu item before the page sees it, so every command with a shortcut in a menu runs from the menu event. Not bound: Cut, Copy and Paste (system items, so the editor receives real clipboard events); shortcuts without ⌘ or ⌃ (Shift+Enter must stay a key press); the drawing tools' bare keys.
- **Guard** (`NativeMenuSync.run`): nothing runs while a dialog is open, and an item that has a shortcut does not run while a text field has the keyboard, as the page's own shortcuts behave. A click cannot be told from a shortcut, so a click on such an item while typing in a field is ignored too.
- **Title bar**: the window uses `titleBarStyle: Overlay` with a hidden title (`tauri.conf.json`, macOS only), so the page draws under the system's title bar and the menu bar's row becomes it (`MenuBar.setTitleBar`): the document name and the controls on the right sit in that row, a 78 px inset keeps clear of the close, minimize and zoom buttons, and `data-tauri-drag-region` makes the row drag the window (double-click zooms; both need the `core:window` permissions in the capability file). In full screen the buttons go and the inset stays.
- **Text fields**: the menu takes ⌘A, ⌘Z and ⇧⌘Z from a focused field (the document title, a dialog's box), so `NativeMenuSync` does them in the field (`document.execCommand`) instead of running the document's command. Other menu shortcuts are ignored there. Clicking the document title selects all of it: WebKit drops the selection a focus makes when the mouse button is released, so `DocumentTitle` selects again on that release.

## The phone apps

The iOS app (Android is not started) is the same crate and the same launcher page (`desktop/frontend`) as the desktop app, so the phone shows the live website. Its bundle id is `com.golemdocs.mobile`, signed by the paid team YOPEY YOPEY LLC (`C57E343UU5`, in `tauri.ios.conf.json`; the same team as the Mac Developer ID certificate). `com.golemdocs.app` is taken by a free personal team that built it first: don't use it.

- **What is desktop only**: the native menu bar and the updater. `src/lib.rs` compiles them under `#[cfg(desktop)]`, `tauri-plugin-dialog` and `tauri-plugin-updater` are desktop-only dependencies in `Cargo.toml` (the stores update the phone app). The vault is on iOS too, with a fixed folder (below). The page must not offer them there: `bridge.ts` returns null from `desktopBridge()`, `desktopUpdater()`, `desktopMenu()` and `isDesktopApp()` on a touch device (`isTouchDevice`: iPhone, iPad, Android, or an iPad that calls itself a Mac), and `isMobileApp()` says it is the phone shell.
- **Config**: `src-tauri/tauri.ios.conf.json` overrides the identifier, sets the team and the minimum iOS (15). The Xcode project in `src-tauri/gen/apple` is committed (it holds the iCloud entitlements, `NSUbiquitousContainers` in `project.yml` and `ICloud.swift`; only `gen/schemas`, `build/` and `Externals/` are ignored). After editing `project.yml` run `xcodegen generate` in `gen/apple`. It was made with `cargo tauri ios init` (not through `npx`, or the generated build script calls `npm run tauri`, which does not exist here); don't re-run init over it. A device needs registering in the team's Devices list at developer.apple.com first.
- **Safe areas**: the page is drawn under the status bar and home indicator (`viewport-fit=cover`), so `body` pads itself with `env(safe-area-inset-*)` (`style.css`); nothing else in the flow should pad for them again (the title and format controls in the menu bar are absolutely positioned and would drift out of line). While the keyboard is up `fitVisual` (`main.ts`) sets `--safe-bottom: 0px`, because the home indicator is under it. Fixed-position pieces (the menu drawer, bottom sheets) pad themselves. The insets are 0 in a desktop browser.
- **Testing page changes in the simulator**: with your `pnpm dev` running, build with `--config '{"build":{"frontendDist":"http://localhost:5173"}}'` so the app loads the dev page instead of golemdocs.com (`cargo tauri ios dev` does not find the simulator by name).
- **Try it in the simulator**: `cd desktop && cargo tauri ios build --debug --target aarch64-sim --ci`, then install `src-tauri/gen/apple/build/arm64-sim/GolemDocs.app` (`xcrun simctl install booted <app>`; `xcrun simctl launch booted com.golemdocs.app`). It needs the Rust targets `aarch64-apple-ios-sim` and `aarch64-apple-ios`, Xcode, `xcodegen` and CocoaPods. A device or App Store build is signed by the team in `bundle > iOS > developmentTeam`.
- **Getting files out**: `ui/saveFile.ts` (`saveFile`) is the one way the page hands a file over. On a touch device whose web view can share files (`navigator.canShare`) it opens the system share sheet (Save to Files, AirDrop, Mail), otherwise it downloads through a link; it is used by File › Download and Download All. A web view has no download list, so a link there goes nowhere. The sheet needs a tap just before it: if the browser refuses (the export took too long) `saveFile` falls back to the link.
- **The vault on a phone is iCloud Drive › GolemDocs** (`src/icloud.rs`, `gen/apple/Sources/golemdocs-desktop/ICloud.swift`): the app's iCloud container, shown in the Files app and on every Apple device. Nothing is chosen (`DesktopBridge.fixed`, no Choose or Stop in the dialog). The Mac vault can be pointed at the same folder (`~/Library/Mobile Documents/iCloud~com~golemdocs~mobile/Documents`). The sync state (`.golemdocs/`) is kept in the app's local data folder on the phone (`Vault.state_home`), not in the shared folder, so the phone and the Mac never overwrite each other's. iOS cannot sync in the background: `VaultService` runs while the app is in front and when it comes back (`visibilitychange`). A file iCloud has not downloaded is a hidden `.name.icloud` placeholder; the scan would skip it and the sync would delete the document from the account, so `vault_scan` instead asks iCloud to download every placeholder and answers `icloud-downloading` (`ICLOUD_DOWNLOADING`), and the service waits and looks again. Needs the iCloud entitlements on a paid team. The Swift functions are defined by the app, not the Rust library, so `build.rs` lets the Rust dylib (which Cargo also links, and iOS never uses) leave them undefined (`-undefined dynamic_lookup`); without that the build fails at the dylib link.
- **Getting the phone to see page changes**: the shell shows golemdocs.com, so page changes need a deploy, or a build with `frontendDist` set to a dev server the phone can reach.
- **Android** (`src-tauri/tauri.android.conf.json`, `src-tauri/gen/android`, committed): the same shell, package `com.golemdocs.mobile`, with no vault yet (`lib.rs` gives it an empty handler). Needs a JDK 17, the Android SDK (platform 35+, build-tools, NDK 27) and the four Android Rust targets; set `JAVA_HOME`, `ANDROID_HOME` and `NDK_HOME`, then `cargo tauri android build --debug --target aarch64 --apk` (the APK is under `gen/android/app/build/outputs/apk/universal/debug`) and `adb install -r` it; an `arm64-v8a` Android 15 emulator image runs it on Apple silicon. The web view gives the page no dependable `env(safe-area-inset-*)`, so `MainActivity.kt` pads the window by the system bars, the cut-out and the keyboard and consumes those insets (the page's own safe-area padding is then 0). Tapping a document opens the keyboard on the first tap, as on iOS. Android's web view has no `navigator.share`, so the shell adds a JavaScript object, `GolemShare` (`ShareBridge.kt`, attached in `MainActivity.onWebViewCreate`), and `saveFile` (`ui/saveFile.ts`) sends the file to it in 768 KiB base64 chunks (`begin`, `chunk`…, `finish`; never one big string). Android writes it to the app's cache (`cache/share/`, read through the FileProvider in `res/xml/file_paths.xml`) and opens the system share sheet; it refuses to share unless the web view is on golemdocs.com or localhost. The web view raises the keyboard for a focused text input as soon as it is touched anywhere (even the menu button), and for any focus made in a tap handler, so on Android `focusInput` (`main.ts`) does nothing except from a tap on the document (`focusByTap`), and the menu drawer closes on a width change only (the keyboard changes the height). The launcher icon (`icon-android.svg`) has a smaller glyph than iOS's, because Android crops an adaptive icon to its middle ~60%. To try page changes in the emulator: run the client dev server from the worktree on another port (`WORD_CLIENT_PORT=5280 pnpm exec vite` in `client`), `adb reverse tcp:5280 tcp:5280` and build with `--config '{"build":{"frontendDist":"http://localhost:5280"}}'`.
- **Receiving files** ("Open in GolemDocs" from Files or Mail, Share to GolemDocs from another app): the system hands the shell a file, the shell copies it into its cache and keeps a list, and the page (`desktop/incoming.ts`, `incomingBridge` / `watchIncoming`) takes the list when it starts, when the app comes to the front (`visibilitychange`) and on a `golem-incoming` window event, reads each file, tells the shell it has it (the copy is deleted) and opens it through the same `dropFile` that handles dropped files (one file opens, several are imported; `droppedFromFiles`). The page names a file only by an id the shell gave it. **iOS**: `project.yml` declares the document types (`CFBundleDocumentTypes`, Markdown imported as `net.daringfireball.markdown`, `LSSupportsOpeningDocumentsInPlace` off so iOS hands over a copy); Tauri reports them as `RunEvent::Opened` (tao's `scene:openURLContexts`), `src/incoming.rs` copies the files and nudges the page (`incoming_pending`, `incoming_read`, `incoming_done`). **Android**: `AndroidManifest.xml` has VIEW and SEND/SEND_MULTIPLE filters for the same types; `IncomingFiles.kt` copies each file from its `content://` address at once (the permission lasts only as long as the intent) and `OpenBridge.kt` (`GolemOpen`) gives the page the list and the bytes in 768 KiB base64 pieces, only to golemdocs.com or localhost. To try it in the simulator or emulator: `xcrun simctl openurl booted file:///tmp/x.md`; on Android, put a file in the app's cache (`adb shell run-as com.golemdocs.mobile`) and `adb shell am start -a android.intent.action.VIEW -t text/markdown -d content://com.golemdocs.mobile.fileprovider/my_cache_images/<path> -n com.golemdocs.mobile/.MainActivity`. A fresh worktree's `gen/apple` needs an empty `assets` folder before `xcodegen generate`, and `gen/android/.../generated/` (gitignored) is only written when `tauri-build` runs, which a shared `CARGO_TARGET_DIR` can skip in a fresh checkout: `touch desktop/src-tauri/build.rs` and build again (a build then fails with "Unresolved reference: TauriActivity" until it has run).
- **Store builds**: `cargo tauri ios build --export-method app-store-connect` (the committed `ExportOptions.plist` says `debugging`, for device builds), with `--build-number <n>` rising on every upload: the CLI writes the app's `version` into `CFBundleShortVersionString` and the build number into `CFBundleVersion`, so `project.yml` sets neither. `Info.plist` says the app uses only exempt encryption (`ITSAppUsesNonExemptEncryption`), and `golemdocs-desktop_iOS/PrivacyInfo.xcprivacy` is Apple's privacy manifest: the required-reason APIs the app calls (file dates for the vault, Rust's clock, its own defaults). Add to it when native code starts calling another API on Apple's list. Android's `versionCode` is derived from the version by the CLI; a release AAB (`cargo tauri android build --aab`) is signed with the Play upload key from `gen/android/app/key.properties` (gitignored: `storeFile`, `storePassword`, `keyAlias`, `keyPassword`) or the `ANDROID_KEYSTORE_PATH`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD` variables, and is unsigned without them. `proguard-rules.pro` keeps the `@JavascriptInterface` methods of the two bridges, which the release build's R8 would otherwise be free to strip. If `xcode-select` points at the Command Line Tools, run the iOS build with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`.
- **No buying in the phone apps**: the App Store and Google Play require their own in-app purchase for a digital subscription and forbid pointing to another way to pay. So `sellsSubscriptions()` (`subscription.ts`) is false in the phone shell: Subscribe and Manage Subscription are hidden (the File menu, the account panel, the assistant's gate), `subscribe()` and `manageSubscription()` do nothing, and the messages that would say to subscribe say instead that the account doesn't include it. A plan bought on the website works in the app as it does anywhere.
- **Not done**: the phone layout is the website's `mobile` profile as it is (menus and toolbars are the desktop's), no document or share extensions, no in-app account deletion (both stores require it), sign-in through the system browser (Google refuses to sign in inside an embedded web view), and the store builds are not made by CI.

## Not built yet

- A bundled client that works offline: it needs token auth on the API, because the page would no longer be same-origin with it. The phone apps show the website too, so they need a connection until this exists.
- An end-to-end test: Playwright drives Chromium, which has no native shell. The driver and codec are covered by `vaultSync.test.ts` and `vaultCodec.test.ts`, the folder rules by the Rust tests.

## Running it

The dev server must be running (`pnpm dev`, started by you, see AGENTS.md); then:

```bash
pnpm desktop:dev
```

`pnpm desktop:test` runs the Rust tests; the planner is tested with the rest of the client (`client/test/vaultPlan.test.ts`). `pnpm desktop:build` makes the installer for this machine (unsigned); the signed installers for a release are built by CI, see [Releasing the desktop app](desktop-release.md). It needs Rust and `cargo-tauri` (`cargo install tauri-cli`); there is no npm dependency.
