# Document formats

The editor works on one in-memory model (`WordDocument` from `@golemdocs/docx`). Every other file format is an edge: a *handler* reads bytes into the model on the way in and writes the model back to bytes on the way out. This doc covers the handler registry, the format libraries (`docx/`, `odt/`, `pdf/`), the app's own `.wdoc` container, and what each conversion loses.

## How it works

```
 file bytes --sourceFromFile (source.ts)--> DocumentSource {kind,name,bytes}
                                                   |  (posted to the layout worker)
                                                   v
                       layout/layoutWorker.ts load()  -> importDocument(kind, bytes)
                                                   |        HANDLERS[format]() (convert.ts, lazy chunk)
                                                   v
                            { document: WordDocument, extensions }   <- "what the model can't hold"
                                                   |
                      edit as `lens` (the format the document is edited as)
                                                   |
   save:  writeWdoc  (whole document, always)      |   export / switch format:
   .wdoc = docx + extensions/<ns>.json (+ original PDF)   exportDocument(doc, extensions, format, fonts)
```

Key ideas:

- **The model is always Word-shaped.** Markdown, HTML, LaTeX, CSV, pictures and so on are *lenses*: the document is a `WordDocument` plus an `Extensions` bag holding what only that format can express (Markdown front matter, a CSV's delimiter, a text file's BOM and line endings, ODF styles, HTML head/attributes...). Writing a format reads only its own namespace and ignores the rest, so exporting to the original format after any number of switches returns the original (`FormatHandler` doc comment in `client/src/formats/convert.ts`).
- **Picking the handler** is by file name (`sourceFromFile`, `client/src/formats/source.ts`: a table of extension regexes). Exceptions decided by bytes: a `.wdoc` is recognised by its stored `mimetype` entry whatever it is called (saved copies keep the lens's name, e.g. `Report.md`), a ZIP with `word/document.xml` is Word whatever the name (a room that ended writes plain Word under another name), and `.xml` is sniffed for DocBook / JATS / FB2 / OPML (`xmlDocumentKind`). Anything else matching `isTextName` (`textFiles.ts`: logs, config, source) opens as `txt`.
- **Lazy chunks.** `HANDLERS: Record<Format, () => Promise<FormatHandler>>` in `convert.ts` returns static handlers for the tiny ones (`docx`, `txt`, `csv`/`tsv`, `html`, `md` glue, `png`/`jpeg`/`webp`) and `import()`s the rest, so each format is its own chunk. Handlers that share code share a module (`handlers/markup.ts` for LaTeX/AsciiDoc/RST/Org/MediaWiki/Textile/Typst on top of `outline.ts`; `handlers/xmlDocuments.ts`; `handlers/webArchives.ts` for EPUB/MHTML/EML; `handlers/svg.ts`). The `md` handler dynamically imports `markdown.ts` itself so Markdown is one request. The size rules (about 20 kB threshold, no static+dynamic import of the same module) are in `AGENTS.md`.
- **`.doc` (Word 97) is import only**: `docImport.ts` (with `cfb.ts`, the compound-file reader) is imported directly by the layout worker, with no `Format` entry and no export.

## The format libraries

| Package | What it is |
| --- | --- |
| `docx/` (`@golemdocs/docx`) | Dependency-free OOXML reader/writer plus the document model: zip, xml, opc, model (`StyleResolver`, `ListCounter`), math (OMML/LaTeX/MathML), edit helpers, and the search index builder the server also uses (`docx/src/search`). Unmodelled content is kept (`extra`, `Raw`, `Wrapper`) so open then save loses nothing. See [docx/README.md](../../docx/README.md). |
| `odt/` (`@golemdocs/odt`) | `readOdt` / `writeOdt` between ODF 1.3 (`.odt`, flat `.fodt`) and `WordDocument` + `OdtExtension` (styles, sections, frames that the model lacks; `odt/src/extension.ts`). Has no README: start at `odt/src/index.ts`. |
| `pdf/` (`@golemdocs/pdf`) | Dependency-free PDF reader/writer: parser, filters, encryption, fonts, text extraction and reflow (`text/reflow.ts`), content scanning and editing (`edit/`), annotations and forms (`write/`). See [pdf/README.md](../../pdf/README.md) and [PDF editing](../pdf-editing.md). |

## Key data types

- `Format` (`convert.ts`): `'docx' | 'odt' | 'rtf' | 'html' | 'epub' | 'mhtml' | 'csv' | 'tsv' | 'tex' | 'adoc' | 'rst' | 'org' | 'mediawiki' | 'textile' | 'typst' | 'docbook' | 'jats' | 'fb2' | 'opml' | 'eml' | 'ipynb' | 'png' | 'jpeg' | 'webp' | 'svg' | 'svgz' | 'pdf' | 'md' | 'txt'`.
- `FormatHandler { read(bytes) -> {document, extensions}; write(document, extensions, fonts) -> bytes }`.
- `Extensions` (`wdoc.ts`): optional namespaces `md, txt, pdf, odt, html, csv, eml, ipynb, svg, img, vec`. `NAMESPACES` in the same file lists the ones persisted; add a key there too or it is silently not saved.
- `DocumentSource` (`client/src/layout/protocol.ts`): the tagged union (`kind: 'docx' | 'doc' | 'md' | ... | 'wdoc' | 'docx-url' | 'blank' | 'welcome'...`) the worker's `load()` switches on.
- `OpenContent`: an editable model in a non-PDF format, or a PDF's original bytes (a PDF opens as its own pages, not through the model).

## The .wdoc format

The app's native save format (`wdoc.ts`, `WDOC_VERSION = 1`): a ZIP whose first entry is a stored `mimetype` (`application/x-golem-document`, so `isWdoc` can sniff the first bytes), then `manifest.json` (`WdocManifest`: `version`, `lens` = format being edited as, `origin` = format first imported, `pagesCurrent`), `document.docx` (the flowing document, absent for a PDF not yet reflowed), `extensions/<ns>.json`, and `originals/source.pdf`. A file with a newer `version` is refused rather than misread. Everything stored in the browser and cloud is a `.wdoc` (see [Storage and sync](storage-and-sync.md)); the server only needs the inner `document.docx` (`server/src/stored.ts`).

`roomDoc.ts` is the variant for collaboration: a room's document is a `.wdoc` unless it is plain Word with no extensions, in which case it stays a plain `.docx`. `roomKind(format)` says whether a room edits `doc`, `objects` (PDF), `layers` (pictures) or `nodes` (SVG drawings). See [Collaboration](collaboration.md).

## Markdown, text and Obsidian-style import

- **Markdown** (`markdown.ts`, hand-rolled CommonMark + GFM tables/strikethrough) maps to model conventions documented at the top of that file: `Heading1..6` styles, `Quote`, `Code` paragraphs, real numbering, task items, tables with a header row. YAML front matter is split off (`splitFrontMatter`) into `extensions.md.frontMatter` and written back verbatim. Comments round-trip as CriticMarkup (`{==text==}{>>comment<<}`). Footnotes and raw HTML stay literal text. Nothing throws on odd input: unknown syntax degrades to text.
- **Obsidian-style links**: `[[Note]]`, `[[Note#Section]]`, `[[Note|label]]` and `![[embed]]` read to hyperlinks with a `doc:` address (`wikiLinks.ts`: titles, not ids, so links survive moves and other browsers; address helpers live in `@golemdocs/docx` `search/links.ts`, where the server-side index reads them too). Embeds stay placeholder links until `resolveEmbeds` (`embeds.ts`) looks the target up. Links that name folder paths follow renames and moves through `client/src/linkRename.ts` and `docLinks.ts` (`rewriteDocumentLinks`).
- **Plain text** (`handlers/txt.ts`, `plainText.ts`, `textFiles.ts`): encoding, BOM and line ending are kept in `extensions.txt` and restored on write. Files of 8 MB or more open in the large-text editor instead (see [text-files.md](../text-files.md)).
- **CSV/TSV** open in the grid (`sheet/delimited.ts`) and are kept as the files themselves; as a lens (a document converted to or from one, a `.wdoc` saved before they opened in the grid, which `formats/wdocDelimited.ts` turns back into the file on opening) they keep delimiter, line endings and encoding in `extensions.csv`. A file with a layout (column widths and the like) is kept whole in a `.wdoc` with no document (`Wdoc.delimited`, `extensions.csv.layout`; see "A CSV's layout" in [spreadsheets.md](../spreadsheets.md)). Excel Workbook is a Convert To target: a document's first table becomes its sheet (`handlers/xlsx.ts`); between Excel, CSV and TSV a workbook stays in the grid (`saveAs` in the sheet worker).
- **Books** (EPUB) open read-only (`editable: false` in `FORMATS`, `book` in the layout worker, which makes the document `readOnly` and leaves out the squiggles): a book is read, so it is never edited or written back, and Convert To makes something to edit from it. Its pages turn with the keyboard (Page Down/Up, Space, the arrow keys: `turnPage` in `main.ts`) and on a touch screen with a tap on the left or right third or a sideways swipe while the page fits the window's width (`bookTapTurn`, `bookSwipe`; the text input gets `inputmode="none"`, so no on-screen keyboard), Convert To saves a new document beside the book rather than replacing it (`keepBook` in `convertTo`), the status bar shows how much has been read instead of the word count, and it opens where it was last read on any device: the worker posts `book` with the book's key once it is open, `goTo` brings a place to the top of the view through the layout updates' `keep` as the pages up to it are laid out, and `textAt` reads the place back. The worker posts `book` before `opened` and before any page, so a book reopened at its place keeps its pages hidden until that place is laid out (`hidePagesForPlace`; the loading screen comes up if it takes more than 600 ms) rather than showing its first page and jumping (see Reading places in [storage-and-sync.md](storage-and-sync.md)).
- **Workbooks** (`.xlsx`, `.xlsm`, `.xltx`, `.xltm`) are not documents: they open in the spreadsheet editor (`client/src/sheet/`, see [spreadsheets.md](../spreadsheets.md)) and are stored as the `.xlsx` itself. Their `FormatHandler` (`handlers/xlsx.ts`, its own chunk) is for what only a document does: Convert To and Print take the active sheet as a table (as shown, up to 20,000 rows), and a document's first table becomes a one-sheet workbook. Search indexes a workbook's rows (`formats/docBytes.ts`).

## Live blocks

A live block (`client/src/live/`, plan in [live-blocks.md](../live-blocks.md)) is a content control in the model, `w:sdt` with `w:tag w:val="live:<source> stamp=<hash>"` and `w:lock sdtContentLocked`, holding its last result: block-level for a table or picture, inline for a value. The stamp is a hash of the result, so a block is rewritten only when what it shows changes. Each host format writes it its own way and reads it back to the same wrapper:

- **Word**: the content control as is.
- **Markdown**: `<!-- golem:live SRC stamp=H -->`, a blank line, the result, a blank line, `<!-- /golem:live -->`; inline, the two comments around the value (`live/markdownMarks.ts`). A plain `![[Budget.xlsx#X]]` of a spreadsheet or CSV, or any `![[…#table:…]]`, `#chart:` or `#field:` address (`isLiveSourceName`), reads as an empty live block, filled at the next update.
- **HTML**: `<div>` or `<span>` with `data-golem-live` and `data-golem-stamp`.
- **ODT**: a `text:section` named `live:…`, or a `text:text-input` described `live:…` for a value (`odt/src/live.ts`).
- Other formats write the result only (Convert To says so).

Producers (`live/sources.ts`, `live/sheetSource.ts`, `live/textSource.ts`) turn a source file's bytes and the part after `#` into a neutral `LiveResult` (`live/result.ts`). `live/update.ts` puts results in place. `live/stored.ts` does it for stored bytes, of a `.wdoc`, Word, or a text file kept as uploaded, and unwraps a CSV kept in a `.wdoc`. A text document gives a heading's section or a bookmark as a `blocks` result (its blocks, placed in the host with their styles, lists and pictures by `adoptBlocks` from `embeds.ts`, live blocks inside made plain and bookmarks dropped), `table:Title` as a table (Word's table title or a caption), and `field:key` from Markdown front matter as a value. A workbook's `chart:Title` (or `chart:Sheet!Chart 2` for one without a title) is laid out as the sheet draws it (`chartScene`), written as SVG (`live/chartSource.ts` `chartSvg`) and pictured as PNG through the drawing reader and painter (`vectorDoc.ts`, loaded when first needed), so it is a picture result like a drawing. A workbook is a host too: a live range is a hidden defined name `_golem_live_<n>` whose comment holds the tag (`live/sheetRanges.ts`). `live/sheetHost.ts` fills it from a table or value result (numbers as numbers, each cell keeping its style), clears what an old, larger result filled, moves the name, recalculates and writes the workbook; `stored.ts` sends stored workbooks there. In the sheet editor a pasted live link is the `addLive` edit, and the sheet worker refuses edits whose cells (`contentsWritten`) run into a live range. The search index lists a workbook's live sources (`workbookIndexed`), including the other workbooks its formulas read: their kept values (`sheet/externals.ts`) are refreshed by `refreshExternals`. A PDF is a source and a host through its form fields (`live/pdfLive.ts`): `Return.pdf#field:Total` is the field's value, as filled in or as in the file, and a field whose `FormField.live` holds a tag is filled from its source (text into a text field or drop-down, yes or no for a check box); only the stored list of fields changes, and the vault's `.pdf` is written from it as any filled-in form is. A live link pasted into a field in Fill In makes it live (`ui/formLayer.ts`), which then shows it read-only; Edit Form shows its source and Stop Updating. Edit PDF's added text boxes and pictures are hosts too (`PdfEdit.live` on `textbox` and `image` edits, `updateEditsLive`): a text box takes a value or a table's rows as lines, a picture a PNG or JPEG result, keeping its width and top edge. A live link pasted into a PDF outside a field (`PdfEditTools.addLive`) adds one: a picture when the source shows one (`showsPicture`: a picture or drawing file, a chart, a PDF page), else a text box, which the annotator refuses to type in (`pickedLive`; the text layer is read-only). A PDF's page is a picture source, `Contract.pdf#page:3`: `formats/pdfPageScene.ts` (in the PDF chunk) draws the page of the vault's file (`toVaultFile` for a stored one) as a drawing scene from `interpretPage`: its paths through `pdfDrawings.ts`, its images as `data:` images, its text as glyph outlines from the embedded font programs (`@golemdocs/pdf/fontProgram`), or text in a like font where there is none; the SVG is written from it and the PNG painted as a chart's is. The index lists a PDF's live sources (`segmentsFromBytes`). A drawing is a host through its groups with `data-golem-live` (`live/drawingHost.ts`): `fillGroup` puts a picture result in the group's `<image>` (keeping its box) or a text, table or blocks result in its `<text>` (keeping its place and style, a line a row); `updateStoredDrawing` reads and writes the SVG through the drawing editor's lazily loaded reader and writer, and a stored drawing's picture is made again with `rewriteStoredDrawing`. In the drawing editor a pasted live link is `VectorEditor.addLive`; `main.ts` waits for the change to reach the open document (`VectorSession.settled`) before Update Now. The index lists a drawing's live sources, stored or as a raw `.svg` (`segmentsFromBytes`). A live PDF export (File › Live PDF Copy) is a stored PDF whose `extensions.pdf.export` holds the tag of the document it is made from; `updateStoredPdf` makes it again when that document's stored bytes changed (`documentStamp`), through the lookup's `exportPdf`, which the keeper fills from `KeeperDeps.exportPdf`: the layout worker's `exportCopy` loads the stored document and writes its PDF without touching the open one. Built-in blocks (`@list:`, `@count:`, `@timeline:`; addresses in `live/builtinAddress.ts`, producers in `live/builtins.ts`) read every note of a folder through the lookup's `folder`, which the keeper fills from `KeeperDeps.folder` (`resolveFolder` in `folders.ts`) leaving out the host and anything that shows it; `resultOf` in `sources.ts` is the one place a source becomes a result for every host, and applies an address's options after `?` to a table (`live/tableQuery.ts`: where, sort, columns, limit); `splitAddress` gives title, fragment and options, and docx `sourceTitle` keeps options out of the title the index and renames use. Insert › Live Block (`ui/formatDialogs/liveBlockDialog.ts`) writes the address and pastes an empty block, which the keeper fills. Edit › Copy as Live Link in a document asks the layout worker for the part at the caret (`live/partAddress.ts`); in a PDF it copies the form field being filled in, or else the page in view (`#page:N`). These, the producers and the sheet reader are one lazy chunk. A rename rewrites live tags like links (`docLinks.ts`).

### Scripts

A script is a `.ts` or `.js` file in the vault's `Scripts/` folder (plan in [live-blocks.md](../live-blocks.md) §8). The language and the sandbox are the `@golemdocs/script` package (`script/src/`, MIT, no dependencies): what scripts see, the stripper, the linker, the runtime and its channels. The vault, the runner and the app's side are `client/src/scripts/`, since they read and write documents through the client's formats. As a block's source (`Scripts/x.ts`, `isScriptSource` in `live/scriptAddress.ts`) it is a **producer**: `resultOf` hands it to the lookup's `script`, which the keeper fills from `KeeperDeps.script`. An **action** changes documents: by hand (Tools › Run Script), from a button block (`@run:Scripts/x.ts`, `buttonScript`; the block shows the action's name and its card a Run button), when a document in a folder changes, or on a schedule. The pieces:

- In the package, `index.ts` is types only: what a script exports as `meta` and the API its function is given (`ProducerApi`, `ActionApi`), for the people and agents who write scripts; a script may `import type` from it, since the stripper deletes type imports. `strip.ts` and `tokens.ts` delete TypeScript's types, keeping every line where it was; syntax that makes code (enums, namespaces, parameter properties, decorators) is an error with its line. `link.ts` links a script and what it imports (relative paths inside `Scripts/` only) into `data:` modules named `golem:///Scripts/...`, so errors point at the script's line.
- `runtime.ts` is the code inside the worker, sent as text, so it uses nothing from outside its own function (the `import()` that loads the program and an `__name` shim are in the bootstrap text: bundlers rewrite both). It takes away the network and storage globals, asks the app for every read, and for a producer replaces the clock with `today` and seeds `Math.random`. `host.ts` drives a run over a `RuntimeChannel`: describe (read `meta`), approve, answer requests, time limit (5 s for a producer, 30 s for an action) and size limit.
- `sandbox.ts` is the app's channel: a hidden `srcdoc` frame with `sandbox="allow-scripts"` (an opaque origin) and a `default-src 'none'` policy, starting the worker from a `data:` URL. `nodeChannel.ts` is a Node worker thread, for the tests and `golem run` (not sandboxed, `cli.ts`, `pnpm golem`).
- In the client, `vault.ts` answers requests (`notes`, `read`, `sheet`, `result`, `open`, and for an action that lists sites in `meta.network`, `fetch`, made by the app with `fetchForScript`: https, those hosts, no cookies or redirects), each checked against the folders `meta` asked for, and turns an action's edits into new bytes through the document model (`editedFiles`), so a note keeps its formatting and front matter. `runner.ts` puts these together and records what each producer read; the keeper treats those files and folders (kept across reloads, `state.ts`) as the block's sources.
- `grants.ts` (in the package), `state.ts` and `app.ts` are small and static: what each script is allowed on this device (never synced), turned off, paused after three failures in a row, the run log with the bytes Undo This Run needs (for as long as the page is open), and the triggers. An action never sets itself off; a chain of actions stops after ten. When a document an action changed was changed by something else while it ran (`changedSince`), the action runs once more on what is there now, with what the person allowed for the first run (`RunOptions.allowed`), and fails, writing nothing, if one changed again. A scheduled run is claimed through the account first (`POST /api/script-claims`, `server/src/scriptClaims.ts`, the `script_claims` table), so only one device runs it; without an account the device just runs it.
- `ui/scriptDialogs.ts` asks before a first run (Allow Once, Always Allow), picks a script to run, and is Tools › Scripts.

The runner, the sandbox, the stripper and the linker are in the live chunk (exported through `live/stored.ts`). The client imports the package by subpath (`@golemdocs/script/host`, `/grants`...), never through `index.ts`, so the static part stays small.

## Conversion fidelity

`conversionIsLossy(from, to)` in `convert.ts` drives the "this loses something" warning. Rules in short:

- Same format: lossless. Switching is "up" the ladder text -> Markdown -> Word without loss; Word/ODT/RTF/HTML to Markdown, text or PDF loses styling, layout, comments and anything the target lacks.
- The lightweight markups (LaTeX, AsciiDoc, RST, Org, MediaWiki, Textile, Typst, DocBook, JATS, FB2, OPML, EML, ipynb) are lossy only when going to `txt` or `pdf` (they share Markdown's conventions via `outline.ts`); OPML and FB2 as a *target* are lossy from everything but text/CSV (OPML holds one-line entries; FB2 has no lists or code blocks).
- PDF is fixed layout: export lays the document out and writes real, selectable text (embedded subset fonts where a font file ships with the app, otherwise standard-14 fonts, so non-WinAnsi and CJK text becomes `?`; see header of `pdfExport.ts`). Import (`pdfImport.ts`) *reflows* recovered text and structure into a new document, so anything from a PDF is lossy (vector art such as logos, charts and QR codes is kept as pictures: `interpretPage(page, { paths: true })` keeps the painted paths with their clips, linear and radial gradients (`render/shading.ts`), tiling patterns, dashes, caps and joins, plus pictures drawn turned; `pdfDrawings.ts` groups the paths that touch and makes each group a `Scene` of the drawing editor (`vector/model.ts`), written as SVG by `vector/svgWrite.ts` and, for the PNG beside it, painted by `vector/paint.ts` (so it has no renderer of its own; without a canvas, as in Node tests, the PNG is one transparent pixel), and `pdfPlaced.ts` floats it on its page, with turned and mirrored pictures as Word's own `rot`/`flipH`/`flipV`; rules and boxes around text are left out; mesh shadings, JPEG 2000 and JBIG2 images are not read); text colors come from `extractText` (`TextItem.color`); running heads and feet (`ReflowResult.running`) become the document's header and footer with tab stops and PAGE/NUMPAGES fields; with a page per PDF page (`pageBreaks`, or placed things) the section's bottom margin is kept small so a line a point taller than the PDF's does not spill onto a new page, and a page's first paragraph carries the part of its top offset the margin (capped at a third of the page) cannot; the original bytes ride along in `originals/source.pdf`.
- Pictures are a page showing the image; PNG is lossless, JPEG/WebP compress. SVG stays vector only as SVG/SVGZ/PDF; to a raster it is pixels.
- HEIC/HEIF (iPhone photos) is read-only: `sniffImage` recognises it from its `ftyp` brand and reads the main picture's size (`ispe`, with `irot`) from the `meta` box, and it is turned into a JPEG when opened (the picture format's `read`), inserted or embedded (`toPng`), so a document never holds HEIC. `decodeImage` tries the browser's own decoder first (Safari) and only then `import()`s `formats/heicDecode.ts`, libheif-js with its wasm inlined: a single lazy chunk (over 1 MB) no other code may import statically.
- `.doc` import reads text, character/paragraph formatting, styles, lists, tables, links, inline PNG/JPEG, first-section page setup, comments; not headers/footers, footnotes, text boxes, tracked changes (see top of `docImport.ts`).

## Adding a format

1. Write the reader/writer in `client/src/formats/` (put heavy parsing there, not in the handler).
2. Add `handlers/<name>.ts` exporting a `FormatHandler` (read keeps extras in an `Extensions` namespace; write gives them back).
3. Add the name to `Format` and `FORMAT_LIST`, and a line to `HANDLERS` in `convert.ts` (static import only if a few hundred bytes).
4. If it has extension data: add the interface and key to `Extensions` and to `NAMESPACES` in `wdoc.ts`.
5. Recognise it: a regex and a `DocumentSource` kind in `source.ts` and `layout/protocol.ts`, a `case` in `load()` in `layout/layoutWorker.ts`, and the extension in `stem`.
6. Update `conversionIsLossy`, the Open/Save/Export menus and i18n strings.
7. Tests in `client/test/` (`convert.test.ts`, `wdoc.test.ts` are the models), then `pnpm --filter @golemdocs/client build` and read the chunk list.

## Invariants and gotchas

- `importDocument` must not throw on malformed text input where avoidable; Word `.doc` and encrypted files are refused with an error.
- Never import a handler module both statically and dynamically; the static one defeats the split.
- A `.wdoc` keeps the *lens* name on disk ("Report.md"); always sniff bytes, do not trust the extension.
- Writing must drop exactly what the target cannot express, and nothing in the `Extensions` of other formats.
- `NAMESPACES` (persisted) and `Extensions` (typed) must be kept in step by hand.
