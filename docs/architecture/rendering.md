# Rendering

Golem Docs draws the whole editor surface (pages, text, selection, caret, squiggles) on one WebGL2 canvas. Text is drawn from MSDF glyph atlases, so it stays sharp at any zoom, and the layout worker hands the main thread GPU-ready buffers, so a frame is only a few instanced draw calls. This doc covers the renderer, the font pipeline behind the atlases, the camera and page arrangement, hit-testing, thumbnails, and what a canvas-based editor means for the DOM, accessibility and tests.

## How it works

```
 layout worker (see layout.md)                       main thread (client/src/main.ts)
 ------------------------------                      -------------------------------------------
 PageLayout --encodePage--> EncodedPage  ---post--->  applyLayout(): new GpuPage(encoded, atlases)
 describeFace(metrics) -> FaceDescriptor ---post--->  atlases.define(): GpuFace (glyph table texture
   (once per face, glyph quads/UVs)                     now, atlas .webp fetched async, redraw on load)
 SelectionUpdate (caret, rects, marks)   ---post--->  SelectionLayer.update()
                                                      arrange(): arrangePages() -> page.moveTo(x, y)
                                                      requestRender() -> render() (rAF)
                                                        camera.clamp -> PageRenderer.render(camera, pages, selection)
```

1. **Data crosses as bytes.** Layout writes 20-byte glyph and rect instances directly (`GLYPH_INSTANCE_BYTES`, `RECT_INSTANCE_BYTES` in `layout/src/display.ts`); `encodePage` (`layout/src/wire.ts`) trims those buffers to what they hold (`InstanceList.trim`: they double as they grow, and the page thread keeps a page's instances until it first draws it, so in a long book the spare room added up to gigabytes), moves them into an `EncodedPage`, and they are transferred, not copied. No conversion happens before they become GPU buffers.
2. **`GpuPage`** (`client/src/webgl/gpuPage.ts`) wraps one page: `TextBatch`es (one per face and synthetic style), background and foreground `RectBatch`es, and image items. It keeps page-relative positions and only a per-page origin changes when pages are rearranged. GPU buffers upload on first draw (`batch.prepare`), so pages never scrolled into view cost nothing on the GPU. Until then a page's glyph instances wait on the page thread, which in a book of tens of thousands of pages ran the tab out of memory, so **`PageShelf`** (`webgl/pageShelf.ts`, in the editor and the viewer) packs them (`TextBatch.shelve`: bytes grouped by their place in the instance, then deflated, `webgl/text/instancePack.ts`, about a sixth of the size) a moment after a page arrives unless it is in or near the view, and unpacks them as it comes near: each frame, and as soon as a layout changes the pages, `keep` gets the pages within a screen of the view (`pagesNear`; waiting for the frame would let a sweep pack the page an edit just made, and it would flash blank). A packed batch draws nothing (`prepare` returns null) until it is unpacked, so anything that draws a page off screen brings it back first (`PageShelf.bring`: the saved thumbnail, Convert To a picture, the pages panel, whose `draw` answers undefined to be asked again). Headers and footers arrive later as an overlay (`setOverlay`) because they need the final page count.
3. **A frame** (`PageRenderer.render`, `client/src/webgl/pageRenderer.ts`): binary-search the visible pages (pages are kept sorted by y), clear to the desk colour (a function the renderer is given: the app's colour scheme, or the viewer's), draw sheets (shadow, border, white or dark fill, snapped to whole device pixels), images behind text, background rects, selection highlight, inline images, text batched per face across pages (sorted by layer, then by `face.id`, so each atlas binds once per layer; see below), foreground rects (underlines, borders), squiggles, remote carets, then the caret.
3a. **Pictures** (`webgl/shapes/imageRenderer.ts`): one textured quad per image, its bitmap decoded once (`createImageBitmap`) with mipmaps. A picture that carries an SVG (a drawing: `Drawing.svg`, `images[].svg` on the page) is drawn from the SVG by the drawing editor's own painter (`vector/svgRead.ts` reads it into a `Scene`, `vector/paint.ts` paints it, both lazy chunks) into a texture at the size it is shown at, so it is sharp; until that texture is ready the bitmap shows. Zooming only scales the texture on screen (smooth, no work); once the zoom rests for ~120 ms (or has gone on ~450 ms) the drawing is painted again at the new size and swapped in. Sizes are quantised in steps of root two (`svgRasterScale`), capped at 4096 pixels a side and 12 million in all, so a small zoom does not paint again and an extreme one stays as sharp as the cap allows; far more than needed is shrunk again, and at most 24 drawing textures are kept (those not on screen go first). Pattern fills, gradients, clips, dashes and joins are the painter's (`paintFor`, `patternFor`), so a drawing looks the same in a document as in the editor.
4. **Text shader** (`webgl/text/textShaders.ts`, `textRenderer.ts`): one instanced draw call per batch, a triangle strip whose 4 corners come from `gl_VertexID`. The glyph's quad and atlas UVs are fetched from the face's glyph table texture (`glyphTable.ts`: two RGBA32F texels per glyph, rows of 128 glyphs). The fragment shader takes the median of the MSDF channels, and supersamples with a 2x2 rotated grid when one screen pixel spans more than about 1.5 atlas texels (zoomed-out text). There are no mipmaps, because tightly packed glyphs would bleed. Synthetic italic (skew) and bold (embolden) are uniforms, used when a family lacks the face. An emoji page's face is a color face (`GpuFace.color`, from `FaceDescriptor.color`): its atlas is premultiplied RGBA with three mipmap levels, and the same shader, with `u_color` set, samples it as it is (no median, no skew or embolden, untouched by Dark Pages), faded only by the text's alpha.
5. **Float precision.** `TextRenderer` computes `(batch.origin - camera) * scale` in float64 on the CPU and passes it as a uniform, so far-away pages in a big document stay precise in float32 vertex math.
6. **Zoom and scroll** only change `Camera` state (`client/src/view/camera.ts`) and uniforms; no buffers are rebuilt. A selecting mouse or pen drag (text, cells, or a box around shapes or slides) that reaches an edge of the view, or goes past it, scrolls it (`scrollDragsAtEdges`, `client/src/ui/edgeScroll.ts`, in the editor and the viewer): it watches the canvas's drags from the window, asks each frame whether the drag under way selects (each editor's `isSelecting`; drags that move, size or draw don't scroll), scrolls through the camera (`clampView` keeps it in bounds), and replays the pointer's last move on the canvas so the active editor carries the selection onto what came into view. A big text file scrolls its own selection (`textEditor/view.ts`), and a finger's selection scrolls in `main.ts` (`edgeScroll`) with the same speed curve (`edgeSpeed`). `Camera.scale` is device pixels per document point (`zoom * CSS_PX_PER_POINT * dpr`, `CSS_PX_PER_POINT = 96/72`). Zoom range is 0.01 to 64. The canvas is sized in exact device pixels via `ResizeObserver` (`devicePixelContentBoxSize`), and `dpr` is derived from the real backing store.
7. **Rendering is on demand** (`requestRender` then `render()` in `main.ts`), also driving caret blink (`CARET_BLINK_MS`). After drawing, `render()` positions the DOM overlays (form fields, PDF text layer, comments, rulers, pointer layer) and the hidden `#input` textarea at the caret.

## Fonts and atlases

Documents name Word fonts; we ship open substitutes. `scripts/fonts/` generates the atlases offline (`pnpm fonts`, `scripts/fonts/generate.ts`) and the output is committed under `client/public/fonts/`.

```
sources.ts (FAMILIES, ATLAS)  -->  generate.ts + msdf-atlas-gen  -->  public/fonts/manifest.json
  charset.txt = core charset                                          public/fonts/<id>/<face>.{webp,json,ttf}
  withExtras() = "<id>-extra" page for everything else                public/fonts/<id>-extra/coverage.json ...
  CJK = noto-sans-{jp,kr,sc,tc}-N pages                               public/fonts/noto-sans-jp-1/ ...
```

- **Atlas format:** MTSDF, 48 px/em, 8 px range (`ATLAS` in `sources.ts`); CJK pages use a coarser MSDF (32 px, range 4, 2048x2048). `.ttf` files are copied next to the atlases only so PDF export can embed them; they are fetched only when a PDF uses the face (`FontSet.fontFile`).
- **Manifest** (`FontManifest`, `layout/src/fonts/fontTypes.ts`): families with `wordName`, `aliases`, `faces` (weight, italic, atlas, layout JSON, metrics) and optional `page: { group, order, coverage }`.
- **`FontSet`** (`layout/src/fonts/fontSet.ts`) runs in the layout worker. `resolve({font, bold, italic})` maps a Word name to a family (via `FALLBACK_BY_NAME`, default `Calibri`; a font set without the stand-in, like the [embeddable viewer's](viewer.md), falls back to Calibri) and picks the nearest face, flagging `syntheticItalic` / `syntheticBold`. `ensure(faces)` loads face metrics JSON once each. Loading is injected (`FontJsonLoader`), so layout also runs in Node tests and on servers. Nothing about a face is loaded until a document uses it.
- **Atlas images** load on the page thread (`AtlasLibrary`, `webgl/text/gpuFace.ts`) when a layout update first names a face; the face draws nothing until then. `AtlasLibrary.warm` fetches and decodes the default font's regular and bold atlases at startup (`main.ts`), so they are ready by the first layout.
- **Pages (extras and CJK) are one mechanism.** A family with `page` is never chosen by name. It only draws characters a run's own font lacks, through `RunStyle.fallbacks`. `ensurePages(group, codePoints, styles)` loads the coverage ranges of each page in the group, then the metrics of the first page covering each code point, and returns code points no page has. `ensureCjk(lang, ...)` runs it for a language and its `CJK_SIBLINGS` (zh-Hans and zh-Hant fill in for each other). `pageVersion` bumps when page metrics load, which is part of the paragraph cache key, so affected paragraphs re-lay out.
- **When pages load:** `LayoutSession.create` scans the document (`pagedTextOf`) and loads what it needs before the first layout; `LayoutSession.ensurePages(text)` loads before an edit that types or pastes uncovered characters (`runCommand` in `layoutWorker.ts`). `ensureMath` loads the math font and the math layout chunk only for documents with equations.
- **Main-thread side:** the worker sends a `FaceDescriptor` (`describeFace`) the first time a face is used (`sentFaces` in `layoutWorker.ts`). `AtlasLibrary.define` (`webgl/text/gpuFace.ts`) creates the `GpuFace`, uploads the glyph table, and fetches the `.webp` with `createImageBitmap(premultiplyAlpha: 'none', colorSpaceConversion: 'none')`. A face draws nothing until its atlas arrives, then `onLoad` triggers a redraw. A face larger than `MAX_TEXTURE_SIZE` is skipped with a console warning.
- **Emoji are color sprites, on font pages of their own.** `scripts/fonts/emoji.ts` (`pnpm fonts:emoji`, sources in `EMOJI` in `sources.ts`) reads Noto Color Emoji's bitmaps (`ttf-emoji.ts`: cmap, GSUB ligatures, CBLC/CBDT), keeps each ZWJ sequence under its Unicode spelling (the font also spells each one backwards, for right-to-left shaping), and writes `emoji-<n>/` pages: a lossy WebP atlas of 72 px sprites in a grid of 8-aligned cells with 8 px of padding (so three mipmap levels never bleed), a layout JSON in msdf-atlas-gen's shape with `atlas.type: "color"`, and a glyph per sequence (`sequence`, code points without U+FE0F) or character (`unicode`). They are pages in the group `emoji` (`EMOJI_GROUP`), so they load like any page: their coverage holds *page keys* (`emojiPageKey` in `layout/src/fonts/emoji.ts`: an emoji's first code point, offset by its skin tone, so each tone's people are pages of their own), and `FontSet.ensureEmoji(keys)` loads the pages holding them. `pnpm fonts` keeps the emoji pages in the manifest as they are.
- **Emoji in layout.** `emojiAt(text, i)` finds the sequence that starts at a point (UTS #51: flags, keycaps, ZWJ sequences with their selectors, skin tones and tags; a text-style pictograph such as ☺ is an emoji only with U+FE0F, and U+FE0E keeps any as text). `addEmoji` collects the page keys of a text's emoji (and of a ZWJ sequence's parts, in case the pages lack the whole), which `pagedTextOf` and `LayoutSession.ensurePages` load before layout. A run's emoji pages are the last of its `RunStyle.fallbacks` (from `emojiStart`), tried only for emoji, by sequence (`FaceMetrics.sequence`). In `layoutParagraph` a sequence is one glyph on its first UTF-16 unit (a ZWJ sequence the pages lack draws as its parts); the units after it are *joined*: no width, no caret stop of their own, and no line break before them. A surrogate pair is joined the same way. Joiners and selectors no font draws take no room.
- **Emoji in exports** (`formats/emojiSprites.ts`): PDF export embeds each sprite once as an image with a soft mask and places it where the glyph is (`drawEmoji` in `pdfExport.ts`); picture export draws the sprite; SVG export writes the emoji's characters, each in a text of its own. The atlas is fetched through `FontSet.fontFile` only when an export has an emoji. Where nothing can decode images (a server), emoji are left out of a PDF.
- **Faces made at runtime: a PDF's embedded fonts.** PDF pages (`client/src/formats/pdfPages.ts`) draw each glyph from the font program its PDF embeds where it can. `PdfFaces` (`formats/pdfFaces.ts`) reads the glyph's outline (`FontProgram`, `@golemdocs/pdf/fontProgram`: Type 1, CFF and TrueType, simple and composite fonts, and Type 3 fonts, whose glyph procedures' filled shapes are read as outlines (`glyphProcedure`; one that strokes, shows an image or text, or shades has none)), turns it into a multi-channel distance field (`formats/msdf.ts`, msdfgen's method at the shipped atlases' 48 px/em and 8 px range, so the same shader draws it), and packs the glyphs a page brings into a new atlas, keyed `pdf-font:<n>`. A glyph whose thinnest stroke (`thinnestStroke`) would be under 2 px wide at 48 px/em, such as a Didot or Bodoni hairline, gets a finer field (96, 192 or 256 px/em, with the range scaled to stay the same in ems) in an atlas of its own resolution (`resolution` in `pdfFaces.ts`), since such strokes break up when a coarse field is drawn large. Its `FaceMetrics` carries the atlas pixels, which `describeFace` puts in the `FaceDescriptor` (`pixels`) and `AtlasLibrary.define` uploads instead of fetching. Glyphs are found by `DisplayGlyph.glyph` (the code, or the CID of a composite font) and `GlyphRun.fontDict`. A glyph the program lacks, or a font with no program (the standard 14), is drawn with a substitute face as before. Text painted with a gradient or pattern has each glyph in the paint's color where it stands (`DisplayGlyph.color`, from `paintColorAt` in `render/shading.ts`).
- **Fonts an SVG embeds** (`client/src/vector/fonts.ts`): `@font-face` rules with a `data:` source are loaded with the FontFace API (the page's fonts, or the worker's) for as long as something shows the drawing: `VectorLayer`, the image renderer's drawing, or `sceneToPng` while it paints. Each stylesheet's families get names of their own (`golem-svg-<n>-<m>`, shared by everything showing the same rules, let go of with the last), which `paintScene` (`PaintOptions.fonts`) puts in place of the file's names, so drawings embedding different fonts under one name don't clash and nothing is renamed in the file. Fonts at an address are never fetched. A canvas can't ask for OpenType features, so each list of features the drawing's text asks for (`featuresOf`: `font-feature-settings` and `font-variant-numeric`) loads the embedded faces once more with FontFace's `featureSettings`, and that text is drawn in those (`fontKey` covers the rules and the lists, so a drawing that asks for new features loads again). `letter-spacing` and `word-spacing` are the canvas's own (`spaced` in `paint.ts`), or a character at a time where it has none. PDF export of a drawing (`vector/pdfOut.ts`) does not embed them: it writes standard fonts.
- **What a PDF page paints over what.** A page is drawn as rectangles, pictures, text, rectangles, while a PDF paints in any order. `sortRects` (`pdfPages.ts`) puts each rectangle under the pictures or in front of the text; one over a picture that is painted over again (a panel over a photo, with text or a logo on it) becomes a shape among the vector pictures, at its place in the painting order (`order`, shared by paths, images, rectangles and text). A rectangle over text stays in front of it (it may be covering it up). Rectangles are cut to their clips' boxes, and images to the page and their clips' boxes (`DisplayImage.shown`, drawn through `ImageItem.crop`); an image's clip that isn't a rectangle cuts only to its box in the page view. `sortRects` runs each time a page is read, after `outlineText`, as the pictures' places must come out the same. The page as a drawing (`pdfPageScene.ts`) needs none of this: it keeps the painting order, text included.
- **A PDF's vector art.** The page view asks `interpretPage` for `paths` with `strips: false`: exact rectangles still come as `rects` (cheap, and sharp at any zoom), while curves, slants, and anything filled or stroked with a gradient or pattern come only as paths (`vectorOnly`). `pictures` in `pdfPages.ts` walks those paths and the page's images in painting order (`order`, shared by paths and images) and makes the paths between two images one SVG picture, framed to what they cover: an `ImageItem` whose `svg` part (`pdf-vector:<n>`) the image renderer draws with the drawing painter at the size it is shown, like a drawing in a document, showing a transparent pixel (`pdf-blank`) until it is ready. The SVG is written by `pdfDrawings.ts` (clips, gradients, tiling patterns, and the images in a pattern's cell, which is how Chromium fills a shape with a picture) when the renderer first asks for the part, from the page interpreted again rather than from paths kept since layout, so a long document of line art holds none of its shapes. Like the page's images, these pictures are under the text.
- **Rules from AGENTS.md:** never widen a core charset or add a second path for rare glyphs; add pages. No font data goes into JS bundles.

## Pages, Page Grid, Flow view

- `arrangePages(pages, columns, gap)` (`client/src/document/arrange.ts`) places pages row-major; with one column it is the usual vertical scroll. Page Grid (`arrangeGrid`) picks the column count that best matches the viewport's aspect ratio, and keeps it while it stays close (`gridColumns`), so pages arriving don't reshuffle the grid. While a document is first laid out the worker sends how many pages it will have (`LayoutUpdate.expected`: a PDF's page count, or `LayoutSession.estimatedPages` from how much of the text is laid out); the grid holds blank sheets (`BlankPage`, drawn by `PageRenderer.blanks`) for the pages still to come, so it has its final shape from the start. `PageRenderer` culling depends on pages staying sorted by y. A page's optional `shown` band (`shownTop`/`shownBottom`) is the part of it on view: View › Hide Space Between Pages (or a double-click on the seam) sets it to the body between the margins (`EncodedPage.body`, from the page's `PageStart`), as Word's Hide White Space does, except at the document's own top and bottom: the first page keeps its top margin and the last its bottom one, so a lone page is shown whole, with its shadow (`joinedBand`), and `arrangePages` stacks those bands edge to edge, so pages overlap by their hidden margins. `PageRenderer` then draws each sheet as its band and each page's content on its own with a scissor clipped to it; hit testing (`pageAt`, `nearestPage`, `onSeam`) and the vertical ruler use the band too. Thumbnails clear it and draw the whole page.
- **Flow view** (`reflowing()` in `main.ts`): the app tells the worker a width (`reflow` message, debounced 150 ms in `syncReflow`); layout then produces one wide column with slim margins and no headers. `renderer.flat = true` draws sheets edge to edge. Flow is off for PDFs, pictures, drawings and the grid.
- A **plain text file** that is large is not a document at all: `client/src/textEditor/` (`glRenderer.ts`, `view.ts`) draws it in chunks on the same camera, reusing `TextRenderer`, `TextBatch` and `AtlasLibrary`. See [text-files](../text-files.md). An emoji there is one character of two cells (`lines.ts`), drawn from its emoji page (`MonoFonts.emoji`, which loads the page the first time a sequence shows).
- A **workbook** is not a document either: `client/src/sheet/renderer.ts` draws it on the same camera in panes (headers and frozen panes, `geometry.ts`), from tiles its worker builds: cells of 64 rows by 16 columns (text laid out on the page with `CellFonts`, `fonts.ts`, drawn as a bar a word below 5 pixels a row; an emoji sequence is one unit there, `eachUnit` in `cellText.ts`, drawn from its emoji page by `CellFonts.emoji` and printed as a picture by `sheetPdf.ts`) and, below 3 pixels a row, an overview of 256 by 256 texels a tile, a square of the sheet in points, drawn by the worker from the same cells and bars, at as many levels as the zoom needs (down to 0.1%). See [spreadsheets](../spreadsheets.md).

## Thumbnails

`client/src/thumbnail.ts` renders a page with the same `PageRenderer` into an offscreen framebuffer (`readPage`), flips rows, forces opaque alpha, and encodes WebP (`capturePageThumbnail`, up to 320x420). They are made on save (stored in IndexedDB, uploaded for cloud documents), backfilled for older documents, and used by the dashboard and the pages panel (`ui/pagesPanel.ts`, drawn lazily for pages in view). The pages panel has items only for the pages scrolled into it: where every item sits is worked out from the page sizes (`ui/thumbList.ts`), a sizer gives the list its full height, items are placed over it and recycled as it scrolls, and each says its place (`aria-posinset`, `aria-setsize`) so a screen reader hears the whole list. The focused item and a dragged one are kept while scrolled away. One item per page took a gigabyte and minutes for a book of 50,000 pages. A page whose glyphs `PageShelf` packed is brought back before its picture is taken. It saves and restores GL state the frame loop relies on.

## Hit-testing and input

Hit-testing splits across the thread boundary. The main thread owns only geometry:
- `pageAt(cssX, cssY)` in `main.ts` converts through `camera.toDocument`, picks the nearest page (so clicks in the gutter still land) and returns page-relative points.
- It sends `{kind: 'pointer', page: id, x, y, extend?, unit?}` to the worker. The worker's `Editor.hitTest(page, x, y)` (`editor/src/navigation.ts`) scores every `LineRecord` on the page by distance (columns restrict candidates), then picks the nearest caret stop (`LineLayout.stops`) and maps the visible offset to a model offset with `toModel` (`layout/src/offsets.ts`).
- Links and task-list check boxes are asked asynchronously (`linkAt`, which also returns a link's shown text). Resting the pointer on a link opens `ui/linkPopover.ts`: a form over the document with the link's text and address, whose OK / Remove Link put the caret in the link and run `setLink` / `removeLink`. It goes when the pointer leaves unless it has been used. The same form is Insert Hyperlink (`LinkPopover.edit`); there is no modal link dialog. The caret and selection come back as `SelectionUpdate` (page-relative points) and are drawn by `SelectionLayer` (`webgl/selectionLayer.ts`) as rects over the same pages, so text and caret update in the same frame.

## Canvas consequences

- **There is no text in the DOM.** Typing goes into a hidden `<textarea id="input" aria-label="Document">` that is moved to the caret each frame, so IME candidate windows and the on-screen keyboard appear in the right place. Keys, composition and clipboard go through it.
- **Screen readers cannot read the canvas.** In Screen Reader Mode the page describes it in invisible HTML instead: the text near the caret in the input textarea, and the pages in view as a reading layer over the canvas. Windows contrast themes reach the canvas only through the `u_forced` shader uniforms. See [Accessibility](accessibility.md).
- **DOM overlays** sit above the canvas for things that need real inputs or are easier in HTML: PDF form fields (`ui/formLayer.ts`), PDF text editing (`ui/pdfTextLayer.ts`), comments (`ui/commentsPanel.ts`), other people's pointers (`ui/pointerLayer.ts`), crop and draw layers. Each has a `position()` called from `render()`.
- **No browser find or spellcheck on the page.** Find, spelling and grammar squiggles are drawn by the worker's geometry (`spellMarks`, `squiggleRects`).
- **How e2e reads text** (`e2e/fixtures.ts`): `main.ts` exposes `window.selectionState` (`caret`, `text`, `others`), `window.loaded`, `window.pages`, `window.status`, `camera`, `pageAt`, `send`. `app.text()` presses Ctrl+A and reads `selectionState.text`. Plain text files expose `window.textEditor.text()`. Other checks use DOM of menus and dialogs, or downloaded files. Pixel assertions are rare.
- **WebGL2 is required**: `main.ts` throws `app.webglUnsupported` if no context. The context is created with `antialias: false, alpha: false, premultipliedAlpha: true`; blending is premultiplied (`ONE, ONE_MINUS_SRC_ALPHA`).

## Key data types

- `EncodedPage`, `EncodedText`, `FaceDescriptor` (`layout/src/wire.ts`): the worker-to-GPU contract. Glyph instance: x, y (float32 points, page-relative), size, glyph index (uint16), packed RGBA8 colour.
- `GpuPage`, `GpuFace`, `TextBatch`, `RectBatch`: GPU-side holders. `TriangleBatch` (`webgl/shapes/triangleBatch.ts`) is the same for triangles (x, y and a colour per vertex), drawn by a spreadsheet's charts (slanted lines, slices, areas). `Camera`: `x, y, zoom, width, height, dpr`.
- `ResolvedFont` / `ManifestFamily` / `ManifestFace` and `page` groups: font resolution.

## Invariants and gotchas

- Pages must stay sorted by y (row-major) or culling breaks. Change page order only through `arrange()`.
- Face ids (`GpuFace.id`) drive draw order; batches of one face should be adjacent. So text of two faces has no order between them unless it is on different layers: `PageLayout.glyphList(font, metrics, layer)` keeps a list per face and layer, `page.glyphs` stays in layer order (so PDF export, page pictures and SVG draw the layers in turn), the layer travels in `EncodedText.layer` to `TextBatch.layer`, and the renderer draws every batch of a lower layer first. Layout puts everything on layer 0; a PDF page (`textLayers` in `formats/pdfPages.ts`) lifts a run one layer above earlier text of another PDF font it overlaps (a white caption over the dark halo a browser writes as a Type 3 font of stroked letters), which few pages have, so ordinary pages draw as before.
- A PDF's outlined text (render modes 1, 2, 5 and 6: `GlyphRun.stroke`, with the interpreter's `paths`) is not something an atlas can draw: its glyphs' outlines become a stroked shape (`strokedTextPath` in `formats/pdfDrawings.ts`, `outlineText` in `pdfPages.ts`) drawn among the page's vector pictures at its place in the painting order, and a run that is only stroked is not drawn as text too. The page-as-a-drawing export (`pdfPageScene.ts`) does the same, and keeps everything in the order the page painted it.
- A page's `EncodedPage` buffers are transferred: the worker must not touch the `PageLayout` buffers afterwards.
- Atlas textures must reach the GPU unmodified (no premultiply, no colour management).
- New faces are registered for every document, even stale ones (`LayoutClient.receive`), because the worker will not resend them.
- Adding a font or charset changes committed binaries under `client/public/fonts/`; run `pnpm fonts` and check the manifest. The `.ttf` copies exist for PDF export. Emoji pages are made separately (`pnpm fonts:emoji`).
- Every renderer that draws `GlyphList`s must handle a color face (`FaceMetrics.color`): draw it through a `GpuFace` (which knows from `FaceDescriptor.color`), or as a picture, never as a distance field.
- Dark Pages is a shader-side colour mapping (`DARK_PAGES_GLSL`), not a different layout; thumbnails pass `darkPages` explicitly.
- After changing the look the marketing clips show, re-record them (see AGENTS.md, `pnpm record:home` and `pnpm record:workbook`).
